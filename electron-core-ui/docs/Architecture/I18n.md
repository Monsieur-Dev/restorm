# I18n

Translation is split across the two processes, backed by the same `translation.json`
resource files, and kept in sync over IPC.

| Layer | Entry point | Backing |
|-------|-------------|---------|
| Renderer | `initializeI18n(resources, defaultLanguage?)` (`electron-core-ui/renderer`) | `i18next` + `react-i18next` |
| Main | `i18nService` (`electron-core-ui/main`) | Hand-rolled key-path lookup (`I18nService`) |

Both are generic — no restorm/demo-specific logic lives here. Each host app supplies
its own `resources`/`translations` on top of ECUI's built-ins (`coreResources` in
`renderer/i18n.ts`, `loadBuiltInTranslations()`/`addTranslations()` in `I18nService`).

## Initial-language resolution (renderer)

`initializeI18n` resolves the language to boot into, in this priority order:

1. **Explicitly stored user preference** — read via `window.api.i18n.getLanguage()`
   (empty string means "nothing stored yet", never a language guess — see below).
   Used only if it names one of the merged `resources` languages.
2. **OS/browser locale** — `navigator.languages` (most-preferred first), then
   `navigator.language`, matched against the merged `resources` languages via
   `matchSupportedLocale` (`electron-core-ui/src/shared/localeMatch.ts`): exact tag
   match first (case-insensitive, so `fr-FR`'s casing never matters and `zh-CN`/`zh-TW`
   resolve to their own regional variant), then base-language match (`fr-FR` → `fr`),
   then best subtag overlap among same-base-language codes so an OS locale carrying a
   script subtag still lands on a shipped variant (`zh-Hant-TW` → `zh-TW`, bare
   `zh` → `zh-CN`) rather than falling through to English.
3. **Caller's `defaultLanguage`** (defaults to `'en'`) — used only when nothing in
   steps 1–2 matches a shipped language.

Once i18next initializes, `initializeI18n` reports the resolved language back to
main via `window.api.i18n.setLanguage()`, which persists it — so the very first
resolution (however it was reached: an explicit choice or an OS-locale guess) becomes
the "explicitly stored" value for the next boot. A user changing the language in
Settings persists the same way and always takes effect immediately (`i18n.changeLanguage`
fires the `languageChanged` listener that calls `setLanguage` too).

`matchSupportedLocale` is a small pure function with no Electron/DOM dependency, so it
is shared verbatim by any process that needs OS-locale matching, not just the renderer
bootstrap above — it is exported from both `electron-core-ui` (main) and
`electron-core-ui/renderer`.

## The `i18n:get-language` / `i18n:set-language` IPC contract

- `i18n:set-language` (`window.api.i18n.setLanguage(lang)`) — always persists `lang`
  via `StorageService` under the `'language'` key and updates `i18nService`'s active
  language. When `lang` differs from the language main was already on, it also
  rebuilds the settings search index (`SettingsService.reindexSearch()`), which is
  built in main from `i18nService.t(titleKey)` and would otherwise stay indexed in
  the previous language. This matters on first boot in particular: the renderer
  resolves the OS locale and reports it here, a transition main sees but the
  renderer does not (its own language never changed), so its own
  reindex-on-language-change never fires for it.
- `i18n:get-language` (`window.api.i18n.getLanguage()`) — returns **only** the
  persisted value, or `''` if nothing has been explicitly stored. It deliberately does
  **not** fall back to `i18nService.getLanguage()` (main's own currently-active
  language): the renderer's step 1 above treats any non-empty result as "the user
  chose this" and skips its own OS-locale fallback (step 2) entirely, so leaking
  main's best-guess active language through this channel would look identical to an
  explicit choice and silently defeat OS-locale detection.

## Main process (`I18nService`)

`i18nService.initialize(resourcesPath, defaultLanguage = 'en')` seeds the
main-process translator (used for native dialogs/menus shown before the renderer's
first `setLanguage` round-trip) with `defaultLanguage` unless a language was already
persisted from a previous run. It does not itself read `app.getLocale()` — Electron
only guarantees a correct result from that call once `app.whenReady()` fires, well
after this is typically called (module-load time), and the renderer's OS-locale
resolution above already covers the actual UI language a moment later. A host that
wants the main-process translator to reflect the OS locale immediately, before any
renderer has booted, should call `i18nService.initialize()` from inside its
`app.whenReady()` handler and resolve the OS locale itself (e.g. via
`matchSupportedLocale` against whatever languages it has loaded).
